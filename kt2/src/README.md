КТ2, ИКБО-10-24, Новожилов Василий Алексеевич.

Процедурная реализация на Python: только функции, dict, list, tuple и set.
Проверено на Python 3.14.3; минимальная версия — Python 3.12.
Сторонних зависимостей нет, requirements.txt не требуется. База данных не нужна.

## Быстрый запуск

Откройте терминал в папке `src` распакованного архива:

```sh
python3 main.py examples/data.json --run 2
```

На Windows вместо `python3` можно использовать `py -3`.

Ожидаемый стандартный вывод, код завершения 0:

```text
Заявка: REQ-001; сервер: SRV-001; прогон: 2
Спецификация: SPEC-1; план: PLAN-1
Предварительный допуск: ДА
```

Первый прогон содержит ошибку памяти. Успешный второй прогон его не перезаписывает:

```sh
python3 main.py examples/data.json --run 1
```

Ожидаемый вывод, код завершения 1:

```text
Заявка: REQ-001; сервер: SRV-001; прогон: 1
Спецификация: SPEC-1; план: PLAN-1
Предварительный допуск: НЕТ
- Тест 2: fail
```

Сохранение полного протокола (конфигурация, результаты, дефекты, инженер, версии):

```sh
python3 main.py examples/data.json --run 2 --output protocol.json
```

Коды завершения: 0 — предварительный допуск; 1 — есть причины отказа;
2 — ошибка аргументов командной строки; 64 — ошибка файла, JSON, модели данных
или неизвестный прогон. При ошибке пояснение выводится в stderr.
Выходной файл не должен совпадать с входным JSON.

## Автоматизируемые операции

| Задача BPMN | Функция | Результат |
|---|---|---|
| Сверить конфигурацию со спецификацией | `check_configuration()` | Недостающие, избыточные и не предусмотренные спецификацией компоненты |
| Проверить готовность протокола | `evaluate_protocol()` | Предварительный допуск и все причины отказа |
| Сформировать протокол | `build_protocol()` | Сводный документ из связанных записей выбранного прогона |

Совместимость деталей и безопасность испытаний инженер проверяет по документации
изготовителя. Программа сверяет модели и количество, проверяет полноту записей;
она не запускает аппаратные тесты и не заменяет решение ответственного за приёмку.

## Данные и логическая модель

`examples/data.json` — полный пример входа. Это один объект с 11 списками.
Каждая запись — словарь, поля перечислены ниже. PK — первичный ключ,
FK — ссылка, AK — дополнительный уникальный ключ. Физические типы СУБД не задаются.

| Набор | Поля и ключи |
|---|---|
| `orders` | PK `id`; AK `number`; `purpose`, `spec_version`; AK `server_serial` |
| `models` | PK `id`; `kind`, `name`; AK (`kind`, `name`) |
| `spec_items` | PK (`order_id`, `model_id`), оба FK; `quantity` |
| `plans` | PK `id`; AK `version` |
| `tests` | PK `id`; AK `code`; `name` |
| `plan_tests` | PK (`plan_id`, `test_id`), оба FK |
| `runs` | PK `id`; FK `order_id`, FK `plan_id`; `number`, `engineer`, `bios`, `bmc`; AK (`order_id`, `number`) |
| `components` | PK `id`; FK `model_id`; `serial`; AK (`model_id`, `serial`) |
| `run_components` | PK (`run_id`, `component_id`), оба FK |
| `results` | PK (`run_id`, `test_id`), оба FK; `status`, `log_ref`, `parameters`, `performed_at` |
| `defects` | PK `id`; FK `run_id`; `description`, `status` |

Идентификаторы, количество и номер прогона — положительные целые числа JSON.
Остальные поля — строки. `results.status`: `pass`, `fail` или `pending`;
`defects.status`: `open` или `closed`. `log_ref` и `performed_at` могут быть пустыми,
но такой протокол не получает допуск. Пустые обязательные строки, лишние поля,
повторные ключи JSON, NaN, неизвестные ссылки и дубли PK/AK отклоняются.
Время хранится как строка; проверяется заполненность, а не календарная корректность.

Все тесты `plan_tests` обязательны. Результат вне плана запрещён; для пары
«прогон, тест» допустим один результат. Благодаря этим условиям недостающие
результаты можно определить как разность числа пунктов плана и результатов.
План и спецификация заявки должны быть непустыми.

Связи M:N разрешены через `spec_items` (заявки и модели), `plan_tests` (планы и тесты)
и `run_components` (прогоны и экземпляры компонентов). Комплектующие одного прогона
не подменяют состав другого. При повторном испытании добавляются новые `runs`,
`run_components` и `results`. Открытый дефект любого прогона той же заявки блокирует
допуск; дефект другой заявки — нет. Закрытый дефект сохраняется в данных.

Пример описывает одну утверждённую спецификацию на заявку. Изменение спецификации,
учёт сотрудников, редактор данных и физическая схема БД — вне текущей реализации.
`engineer` — подпись исполнителя в карточке прогона, а не справочник сотрудников.
Протокол — вычисляемое представление, поэтому отдельной сущности `protocols` нет.
Сведения о BIOS, BMC и результатах хранятся на уровне прогона.

Входные данные и ссылки на журналы в примере учебные. Программа проверяет наличие
ссылки, но не открывает журналы и не подтверждает достоверность аппаратных испытаний.

## Алгоритмы

1. `check_configuration(spec_items, components)` для каждой из n позиций спецификации
   просматривает все m компонентов. Отмечает совпавшие компоненты, затем отдельным
   проходом выявляет лишние. Время худшего случая O(n·m + n + m + 1), при n,m ≥ 1 —
   O(n·m). Дополнительная память с результатом O(n + m + 1).
2. `evaluate_protocol(results, required_count, defects, configuration_issues)` один раз
   просматривает r результатов и d дефектов и копирует e замечаний комплектации.
   Время O(r + d + e + 1) = O(N), N = r + d + e + 1. Память O(N) с причинами отказа.
   Записи результатов должны быть уникальны и входить в план: это заранее проверяет
   `validate_data()`. На блок-схеме изображён именно этот алгоритм после валидации.

Оценки даны в модели единичной стоимости для идентификаторов и полей ограниченного
размера. Для неограниченных строк добавляется суммарная длина обработанных строк L;
память вывода также зависит от длины сообщений. `append()` имеет амортизированную
стоимость O(1), копирование списка — O(e), `len()` — O(1), `strip()` — O(длины строки).
Поиск в словарях алгоритмов выполняется по фиксированному числу имён полей.

Загрузка, проверка ключей и соединение наборов выполняются отдельно в
`validate_data()` и `build_protocol()`. Для T входных записей консервативная оценка
этой подготовки в худшем случае — O(T² + L), в том числе из-за проверок наличия
позиций и возможных коллизий хеш-таблиц. Линейная оценка второго алгоритма не
является оценкой всей CLI-программы. Сортировка и внешние библиотеки не используются.

## Проверки

```sh
python3 test_main.py
```

Ожидаемая последняя строка: `Пройдено: 10 групп проверок`.
Проверяются допуск, отказ, нехватка и избыток деталей, пустой набор компонентов,
пропуски тестов, fail/pending, отсутствие журнала, открытый дефект старого прогона,
изоляция заявок, сохранность истории, PK/FK/AK, ошибки CLI и процедурный стиль.
