# Сопоставление процедурной и объектно-ориентированной версий

Обе версии проверяют комплектацию сервера и готовность протокола приёмки. Объекты данных, правила допуска и границы процесса сохранены из КТ2. Java-версия переносит операции в сервис и объекты правил; изменение архитектуры не меняет результат на общих входных данных.

## Соответствие модели данных

| Набор КТ2 | Класс Java | Смысл |
| --- | --- | --- |
| orders | Order | Заявка на один сервер |
| models | ComponentModel | Модель комплектующего |
| spec_items | SpecificationItem | Требуемая модель и количество в заявке |
| plans | TestPlan | Версия плана испытаний |
| tests | TestDefinition | Определение проверки |
| plan_tests | PlanTest | Включение проверки в план |
| runs | TestRun | Отдельная попытка сборки и приёмки |
| components | Component | Физический экземпляр комплектующего |
| run_components | RunComponent | Участие экземпляра в прогоне |
| results | TestResult | Результат теста в прогоне |
| defects | Defect | Дефект, зарегистрированный в прогоне |

Объединений и разделений сущностей нет. Дополнительные `DataSet` и `RunContext` — снимок всего набора и выборка для одной операции, а не новые отношения логической модели. `ProtocolService` и классы правил соответствуют автоматизируемым операциям. `Json`, `DataValidator` и `Main` обслуживают загрузку, контроль входа и CLI.

Record — специальный вид класса Java с закрытыми final-полями и публичными аксессорами. Сущности используются как неизменяемые значения, а изменяемое состояние проверки локально принадлежит объекту правила на время вызова. Обоснование record-классов: [Oracle, Record Classes](https://docs.oracle.com/en/java/javase/17/language/records.html).

## Таблица сравнения

| Элемент | Python, КТ2 | Java, КТ3 | Что изменилось и почему |
| --- | --- | --- | --- |
| Хранение сущностей | dict с именованными полями, списки записей | 11 record-классов и типизированные списки DataSet | Инкапсуляция и явные границы типов — проектирование; record и статическая проверка типов — язык |
| Сверить конфигурацию со спецификацией | check_configuration(spec_items, components) | ConfigurationRule.check(context) вызывает evaluate(context) | Операция стала поведением объекта правила; вход объединён в RunContext |
| Алгоритм 1 | Вложенные for и список matched | Вложенные for и List<Boolean> matched | Алгоритм и O(n·m+n+m+1) сохранены; синтаксис коллекций относится к языку |
| Проверить готовность протокола | evaluate_protocol(results, required_count, defects, configuration_issues) | ProtocolRule.check(context); ProtocolService объединяет причины | Проверки протокола отделены от комплектации; единый список причин формируется сервисом в прежнем порядке |

| Сформировать протокол | build_protocol(data, run_id) | ProtocolService.buildProtocol(runId) | Сервис хранит проверенный DataSet и набор правил, выполняет выборку и возвращает представление протокола |
| Проверка структуры и связей | validate_data, unique, schema | DataValidator.validate, unique, schema | Граница ввода выделена в класс; неизменные PK/AK/FK и статусы сохраняют семантику |
| Обработка ошибок | ValueError/OSError, argparse | IllegalArgumentException/IOException и CLI-адаптер | Названия исключений и обработчик CLI зависят от языка; коды 0/1/2/64 сохранены |
| История испытаний | Функции не изменяют исходный dict, но вызывающий код может его менять | DataSet копирует вход, коллекции доступны только для чтения | Выбранный дизайн с неизменяемыми значениями предотвращает изменение снимка извне; это возможно и в Python |
| Числа и строки | int произвольной точности; str.strip | BigInteger; Json.blank с согласованным набором пробельных символов | Различия стандартных типов языков; выбор int/long в Java незаметно ограничил бы ID |

| Чтение JSON | Модуль json стандартной библиотеки | Небольшой класс Json, без сторонних зависимостей | Отличие библиотечного окружения, а не достоинство/недостаток ООП |

## Пример изменения

Новая потребность: блокировать приёмку, если в карточке не указан ответственный инженер. Сейчас пустое имя отклоняет валидатор; для демонстрации расширения можно ввести дополнительное предметное правило: подпись не должна содержать служебную строку `не определено`.

В Java добавляется `EngineerSignatureRule extends AbstractAcceptanceRule`. Метод `evaluate(RunContext)` возвращает причину отказа при такой строке, иначе пустой список. Его объект включается после существующих правил в конструкторе `ProtocolService`. Алгоритмы комплектации, проверки тестов и код сервиса менять не требуется. Работа точки расширения уже проверяется тестом `SelfTest`: дополнительное правило передаётся как `AcceptanceRule` и меняет результат только расширенного сервиса. Само новое бизнес-правило в основной режим **не включено**, чтобы сохранить поведение КТ2.

В текущей Python-версии понадобятся новая функция и вызов из `build_protocol` с добавлением причин к общему списку. Это небольшое изменение: утверждать, что процедурная версия обязательно требует множества ветвлений, было бы неверно. Список функций и передача зависимостей доступны и в Python. Выигрыш текущего ООП-дизайна — явный контракт правила и изоляция конкретных проверок; цена — больше типов и файлов.

## Размер и сложность сопровождения

По текущему снимку: Python — 1 производственный файл, 9 функций, 0 своих классов, 212 физических строк; Java — 21 производственный файл, 21 тип (12 record-классов, 8 обычных/абстрактных классов и 1 интерфейс; record-классы также являются классами), 708 физических строк. Поле `classes` в `code_metrics.json` считает объявления с ключевым словом class; интерфейс включён только в общее число `types`. Тесты, примеры и сборочные скрипты не входят в эти числа; пустые строки и комментарии входят. Размер кода не измеряет качество.

Java-разделение делает места ответственности заметнее: внешние данные проверяются один раз при создании снимка, сервис не зависит от конкретного вида правила, сохранённый снимок нельзя случайно изменить через список. Для небольшой CLI-программы исходная Python-версия короче и быстрее просматривается целиком. Дополнительные затраты Java связаны с объявлениями типов, файлами классов, явными преобразованиями данных и собственным JSON-кодеком. Не все эти затраты вызваны ООП.

## Проверка одинакового результата

Вход `kt3/src/java/examples/data.json` совпадает побайтово с примером КТ2. При `--run 2` обе версии выводят:

```text
Заявка: REQ-001; сервер: SRV-001; прогон: 2
Спецификация: SPEC-1; план: PLAN-1
Предварительный допуск: ДА
```

При `--run 1` обе версии дают отказ и `Тест 2: fail`. Команда из корня репозитория `python3 scripts/check_kt3_parity.py` сравнивает 150 случаев, включая 30 сценариев с фиксированным seed. Для корректной модели проверяется полное равенство JSON-протоколов и stdout; для ошибочного ввода — отказ с одинаковым кодом 64. Ещё 7 проверок охватывают CLI и повреждённый UTF-8. Протокол проверки находится в `parity_results.json`; тесты не доказывают эквивалентность для всех мыслимых входов, но покрывают правила и граничные случаи модели.

Сохранены обе оценки сложности из КТ2, при ограниченной длине полей. К стоимости обработки строк добавляется их суммарная длина; операции BigInteger также зависят от разрядности. Для полного запуска отдельно учитываются разбор файла, валидация и выборка связанных данных.

## UML и реализация

`kt3/models/classes.puml` и `classes.png` показывают все 21 производственный тип, видимость, типы полей и методов, обобщение, реализацию интерфейса, ассоциации и агрегацию. Подробности разделены по пакетам; общая схема пакетов находится в `docs/kt3/packages.puml` и `packages.png`. Поля и методы схемы извлечены из скомпилированных сигнатур `javap`, связи описаны по коду и ключам модели.

Полый ромб у набора правил и выборки контекста обозначает агрегацию: включённые объекты могут существовать отдельно и использоваться повторно. Ассоциации с меткой `_id` разрешаются по ключам, а не означают несуществующие Java-поля с объектными ссылками. Конструкторы и стандартные методы record-классов опущены в соответствии с легендой; их поля и аксессоры показаны. Нотация: [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/About-UML).
