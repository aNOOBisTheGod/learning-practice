# Команда для промышленного внедрения системы

Для внедрения системы учёта сборки и приёмочных испытаний предлагаются четыре роли. Это состав будущей проектной команды, а не перечень участников учебной работы. Руководитель приёмки со стороны производства согласует критерии допуска и участвует в приёмке как представитель заказчика.

| Роль | Задачи и артефакты проекта | Профессиональные компетенции | Личностные компетенции | Что подтверждается текущим проектом и что развивать |
| --- | --- | --- | --- | --- |
| Системный аналитик | Согласовать процесс сборки и повторных прогонов; формализовать критерии допуска и регистрацию дефектов; поддерживать BPMN, ER-модель, словарь данных, требования и критерии приёмки | BPMN 2.0, UML, 3НФ, SQL, описание API и интеграций, трассировка требований, интервью с инженерами | Умение уточнять неоднозначности, слушать заказчика, аргументировать решения и поддерживать точную документацию | В проекте есть BPMN, ER, UML и таблица операций. Для развития — реальные интервью, управление изменениями, проектирование API и практический SQL |
| Java-разработчик | Реализовать модель, проверки и протокол; поддерживать CLI; на КТ4 подключить хранилище через JDBC, обеспечить транзакционность и миграции; выполнять code review | Java 17+, ООП, коллекции, исключения, Git, SQL/JDBC, модульное тестирование; позднее Spring и REST | Внимание к контрактам, способность объяснять код, принимать замечания и оценивать последствия изменений | В проекте есть Python- и Java-версии, интерфейсы и тесты. Для развития — JDBC, JUnit, сборка Maven/Gradle, Spring и работа с чужим кодом |
| Инженер по тестированию | Построить тестовую модель; проверить допуск/отказ, комплектацию, ключи и историю; автоматизировать регрессию и сравнение реализаций; подготовить отчёт о качестве | Тест-дизайн, Java/Python, JUnit/TestNG, SQL, тестирование API, логи, Git и CI/CD | Системность, воспроизводимое описание дефектов, внимательность к границам и конструктивная обратная связь | В проекте есть 44 автономные проверки Java и 150 сравнительных сценариев. Для развития — независимый тест-дизайн, JUnit/Mockito, нагрузочные и интеграционные проверки |
| Инженер эксплуатации и DevOps | Автоматизировать сборку и доставку; настроить окружение, логи, резервные копии и восстановление данных; подготовить инструкции развёртывания и отката | Linux, сети, GitLab CI/GitHub Actions, контейнеризация, PostgreSQL, мониторинг; при росте системы — IaC и оркестрация | Ответственность за восстановление, аккуратность изменений, умение разбирать инциденты и передавать знания | В проекте есть воспроизводимая сборка и коды ошибок CLI. Для развития — CI, эксплуатация Linux, резервное копирование и проверка восстановления БД |

На небольшом пилоте роли могут совмещаться, но приёмку собственных изменений желательно проверять другим участником. Аналитик задаёт критерии, разработчик реализует их, тестировщик проверяет, инженер эксплуатации обеспечивает воспроизводимый запуск. На начальном этапе отдельный дизайнер не нужен: продукт работает через командную строку.

Столбец о компетенциях отражает **наличие соответствующих артефактов в учебном проекте**, а не подтверждённую личную самооценку автора. Перед переносом в окончательный отчёт нужно уточнить самостоятельное владение Java, Python, SQL, Git, Linux и тестированием, а также наличие коммерческого опыта. Личностные компетенции нельзя установить по репозиторию; их оценку добавляет автор.
